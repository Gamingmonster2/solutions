# دليل هندسة المدفوعات الهجينة — تطبيق على منصة Solutions

> الحالة: **مسار USDC/Polygon المباشر إلى محفظة المالك مُنفَّذ ومُختبر محلياً** (انظر §11). مسار البطاقة لا يزال مواصفة تصميم فقط ولم يُعتمد له مزوّد.
> اليوم: 2026-11-18. مدة انتقال MiCA (حتى 1 يوليو 2026) **انتهت**، لذلك أي مزوّد في المنطقة الاقتصادية الأوروبية يجب أن يكون CASP مرخّصاً الآن، دون استثناء انتقالي.

## 0. الهدف

القبول بـ **Visa / Mastercard** من العميل، وتسوية العائد إلى **محفظة المالك** بالعملات المشفرة — مع الحفاظ على المسار المجاني وBYOK كما هما.

القاعدة الحاكمة: نحن نبيع **اعتمادات ذكاء اصطناعي / اشتراكات**، لا نبيع عملة مشفرة كأصل. لذلك لا نعتمد نموذج "On-Ramp للمستخدم"، لكن نفترض أن البطاقة + التسوية المشفرة قد تُصنّف quasi-cash من قبل البنك المكتسب؛ تُعلن كما هي ولا تُخفى.

## 1. الفصل المعماري بين الساقات (Three-Leg Architecture)

| الساق | من يدفع | من يستلم | MoR | أثر البطاقة |
|---|---|---|---|---|
| A — قبول البطاقة | العميل (Visa/MC) | مزوّد الدفع | **مزوّد الدفع** (يتحمل الاحتيال والـ chargeback) | MCC يُعلنه البنك المكتسب؛ إن كانت تسوية مشفرة → MCC 6051/6012/4829/6540 + **Special Condition Code 7** |
| B — تسوية المالك | مزوّد الدفع | محفظة المالك (USDC/EURC على L2) | **نحن** كتاجر خدمات رقمية | لا يوجد عكس على البلوكشين بعد التأكيد → chargeback = 0 |
| C — السحب النقدي الاختياري | مزوّد/CASP | حساب EMI/بنكي | مزوّد Off-Ramp | يخضع لـ KYB/exposure disclosure |

**القواعد:**
- لا نختار ولا نعدّل MCC بأنفسنا؛ البنك المكتسب هو الذي يعلنه. نسجّل القيمة المُعلنة في `invoice_events` لأغراض التدقيق.
- لا "توجيه ذكي" يخفي طبيعة النشاط، ولا إعادة محاولة ببيانات مختلفة لتجاوز الحظر.
- إن رفضت البطاقة لأسباب MCC، لا تُعاد المحاولة تحت تصنيف آخر.

## 2. التكلفة الحقيقية (TCO)

```
TCO = Headline Fee + Conversion Spread + Fiat Payout Fee + Network/Gas Fee
```

| البند | بطاقة تقليدية | مشفر → نقد | مشفر → محفظتنا (الهدف) |
|---|---|---|---|
| الرسم المعلن | 1.5% – 3.5% | 0.5% – 2.0% | ~1% (حسب المزوّد) |
| فارق الصرف | — | 0.5% – 1.5% | 0.5% – 1.5% |
| رسم السحب البنكي | مُضمّن | €0.50 + 0.5% أو 1.5% – 2.3% | **0** (لا يوجد سحب) |
| Gas | — | $0.01 (L2) … $2+ (L1) | $0.01 على Polygon/Arbitrum |
| **TCO تقريبي** | **1.5% – 3.5%** | **2.2% – 3.0%** | **~1.5% – 2.5% + gas** |
| Chargeback | نعم، حتى 120+ يوماً | لا | لا |

الاستنتاج الاستراتيجي ليس "العملات أرخص دائماً"، بل **إلغاء مخاطر الاسترداد** + إلغاء رسم السحب عندما تكون الوجهة محفظة المالك مباشرة. حدّ نزاع البطاقات 1.5% هو خط الخطر الذي يفرض إدارة النزاعات حتى لو كانت الربحية أعلى.

**معاملات التكوين المقترحة** (تُملأ من عروض فعلية قبل أي implementation):

```js
// مواصفة مسار البطاقة/المزوّد — لم تُنفَّذ؛ المسار المباشر يستخدم src/config/plans.js
export const PAYMENT_MODEL = {
  quoteWindowMs: 15 * 60 * 1000,   // 10–20 min
  underpaymentTolerance: 0.015,    // 1–2%
  confirmations: { polygon: 64, arbitrum: 20, bitcoin_low: 1, bitcoin_high: 6 },
  settlement: { coin: 'USDC', chain: 'polygon', destination: 'owner_self_custody' },
  fees: { headline: null, spread: null, payout: null, gas: null }, // = null → محظور النشر
}
```

لا تُعرض أي رسوم داخل التطبيق ما لم تُملأ كل الحقول `fees` بعقد أو عرض موثّق.

## 3. قواعد شبكات البطاقات

- **MCC 6051** quasi-cash للمنصات والمحافظ وبوابات التحويل؛ **6012** فقط للبنوك/المؤسسات المرخّصة؛ **4829** للتحويلات؛ **6540** لبطاقات القيمة المخزّنة.
- **Special Condition Code 7** إلزامي في التفويض والتسوية لعمليات شراء الأصول تحت هذه الأكواد.
- **Visa Tier 2** (Risk of Financial Harm) يتطلّب موافقة مسبقة من البنك المكتسب + EDD + تسجيل المعاملات بدون بطاقة.
- **Visa Ramp Provider Program**: تسجيل مزوّدي On/Off-Ramp كـ TPAs تحت HIR، مع مؤشرات على مستوى المعاملة: سعر تحويل لحظي، نوع العملة المستقرة، بيانات NFT إن وُجدت.
- قاعدة حازمة: لو اشترى العميل مشفراً عبر Ramp ثم استخدمه في موقع مراهنات تابع، يجب تحويل المعاملة إلى **MCC 7995** — لا يجوز تركها تحت 6051. مخالفة إخفاء البيانات تصل إلى **$25,000/شهر** لكل تاجر مخالف + حظر نهائي.

**ما نطبّقه في الكود:** تسجيل `declared_mcc`, `condition_code`, `provider`, `rate_indicator` في كل فاتورة؛ رفض أي webhook يحاول تعديلها؛ تدقيق دوري.

## 4. الامتثال حسب المنطقة

| الإطار | المتطلب | أثرنا |
|---|---|---|
| **MiCA** (EU 2023/1114) | انتهت المهلة الانتقالية 1 Jul 2026؛ التعامل فقط مع **CASP** مسجّل؛ العملات المقبولة في EEA هي **EMT** فقط: USDC, EURC, EURI, EURCV, EURe, EUROe, EURD — USDT غير مسموح | إن خدمنا عملاء EEA → التحقق من CASP في السجل الرسمي واستخدام USDC/EURC فقط |
| **EU 2023/1113 / FATF Travel Rule** | حد صفري بين CASPs، بروتوكول **IVMS101**؛ تحقّق من ملكية المحفظة غير الحاضنة فوق **€1,000** | تخزين بيانات الأمر/المستفيد في `invoice_events`، ومنع الإرجاع لمحفظة غير مُثبتة |
| **FinCEN** (FIN-2019-G001) | معالجو المشفر = MSB / Money Transmitter؛ تراخيص فيدرالية + ولاية (BitLicense) | يمنع التعاقد مع مزوّد غير مرخّص حتى لو كان أرخص |
| **UK FCA MLRs** | Cryptoasset Exchange Provider أو Custodian Wallet Provider → تسجيل FCA مباشر | نفس شرط CASP للمملكة المتحدة |
| **حماية الحساب البنكي** | KYB/UBO → حساب **EMI** مخصص (مثال: €500 تأسيس + €50/شهر، ~أسبوع) → إفصاح مسبق عن مصدر الأموال → مزوّد مرخّص (~5–7 أيام عمل لـ high-risk acquiring) | لا استلام تحويلات من محافظ شخصية غير معرّفة إلى الحساب المؤسسي |

## 5. دورة حياة الفاتورة (Invoice Lifecycle)

| المرحلة | الآلية | الزمن | من يتحمل الخطر |
|---|---|---|---|
| 1. قفل السعر | تحويل المبلغ النقدي لمعادل مشفر وتثبيت السعر | 10–20 دقيقة (نختار 15) | البوابة/المتجر |
| 2. عنوان فريد | عنوان جديد لكل فاتورة، عدم إعادة الاستخدام | فوري | المتجر إن أخطأ |
| 3. البث | العميل يرسل من محفظته | حسب العميل | العميل |
| 4. التأكيد | 1 تأكيد BTC منخفض القيمة؛ 3–6 للكبير؛ ثوانٍ على L2 | ثوانٍ … 60 دقيقة | المتجر إن سلّم قبل الاكتمال |
| 5. التسوية | تحويل لمحفظة المالك أو نقد بنكي | فوري … 5 أيام | المتجر (الصرف + السحب) |

**نقص الدفع:** إذا خُصم Gas من الإجمالي بدل إضافته، نقبل تلقائياً عند `paid >= amount × (1 − 0.015)`. لا نفتح تذكرة دعم داخل نطاق التسامح.

**منع التكرار (Idempotency):** كل webhook يُخزّن بمعرّف حدث فريد؛ المعالجة مرة واحدة فقط؛ قفل السعر ينتهي تلقائياً؛ الدفع بعد انتهاء النافذة يُعامل حسب سياسة مُعلنة لا تقدير لحظي.

## 6. المرتجعات (3-Point Refund Architecture)

1. **سياسة القيمة:** الإرجاع بـ **القيمة النقدية الأصلية وقت الشراء**، لا بسعر المشفر وقت الإرجاع — منعاً للمضاربة.
2. **Gas:** يُقتطع من المبلغ المرتجع أو يتحمله المتجر حسب سبب الإرجاع؛ يُسجّل في `refunds.gas_allocated_to`.
3. **ملكية المحفظة:** إرجاع حصرياً إلى **عنوان الإرسال نفسه** بعد مطابقة الهوية، مع تحقّق بتوقيع رسالة صغيرة (micro-signature). لا تحويل لعناوين عشوائية.

## 7. مخطط D1 المقترح (لم يُنفّذ)

```sql
-- يضاف إلى worker/schema.sql بعد اختيار المزوّد
CREATE TABLE IF NOT EXISTS plans (
  id TEXT PRIMARY KEY, name TEXT NOT NULL, price_minor INTEGER NOT NULL,
  currency TEXT NOT NULL, credits INTEGER NOT NULL, active INTEGER NOT NULL DEFAULT 1
);
CREATE TABLE IF NOT EXISTS invoices (
  id TEXT PRIMARY KEY, user_id TEXT NOT NULL, plan_id TEXT NOT NULL,
  amount_minor INTEGER NOT NULL, currency TEXT NOT NULL,
  pay_coin TEXT NOT NULL, pay_chain TEXT NOT NULL, pay_amount TEXT NOT NULL,
  receive_address TEXT NOT NULL, quote_expires_at TEXT NOT NULL,
  declared_mcc TEXT, condition_code TEXT, provider TEXT,
  status TEXT NOT NULL, created_at TEXT NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id), FOREIGN KEY (plan_id) REFERENCES plans(id)
);
CREATE TABLE IF NOT EXISTS invoice_events (
  id TEXT PRIMARY KEY, invoice_id TEXT NOT NULL, type TEXT NOT NULL,
  payload TEXT NOT NULL, created_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS webhook_events (
  event_id TEXT PRIMARY KEY, provider TEXT NOT NULL, received_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS refunds (
  id TEXT PRIMARY KEY, invoice_id TEXT NOT NULL, fiat_minor INTEGER NOT NULL,
  crypto_amount TEXT NOT NULL, gas_allocated_to TEXT NOT NULL,
  destination_address TEXT NOT NULL, status TEXT NOT NULL, created_at TEXT NOT NULL

```

المبالغ كلها **بالوحدات الصغرى (minor units)** كأعداد صحيحة لتجنّب أخطاء الفاصلة العائمة.

## 8. مسارات Worker

المسارات المُنفَّذة فعلياً للمسار المباشر (§11):

- `GET /pay/plans` — عام؛ يعرض الخطط وشبكة الدفع وعنوان المحفظة.
- `POST /pay/invoice` — يتطلّب جلسة؛ ينشئ مبلغاً فريداً ويخزّن الفاتورة.
- `GET /pay/status?invoice=...` — يتطلّب جلسة؛ حالة الفاتورة + فحص على السلسلة بمعدل مرة كل 10 ثوانٍ كحد أقصى.
- `GET /account/plan` — الرصيد المدفوع واستخدام الحصة المجانية.
- `POST /pay/scan` — اختياري للعمليات فقط؛ يعمل فقط عند ضبط `PAY_ADMIN_TOKEN` كـ secret ويُرسل كـ Bearer.

مسار البطاقة المقترح (لم يُنفَّذ): `POST /pay/quote` و`POST /pay/webhook` مع توقيع webhook آمن/idempotency. لا يوجد أي webhook في المسار الحالي لأن Worker يقرأ السلسلة العامة مباشرة. المفاتيح الخاصة **لا تُخزَّن في Worker** ولا تصل إلى المتصفح.

## 9. بوابات القرار قبل كتابة كود الدفع

1. ✅/❌ الكيان القانوني والولاية القضائية (ليبيا؟ EEA؟ أخرى) وتأثيرها على MiCA/FCA.
2. ✅/❌ مزوّد واحد على الأقل متاح في هذه الولاية، مع KYC مقبول وCASP/ترخيص مُثبت.
3. ✅/❌ مسار **بطاقة → محفظة المالك** حقيقي بأسعار موثّقة (ليس فقط crypto↔crypto).
4. ✅/❌ عملة وشبكة التسوية (المقترح: USDC على Polygon/Arbitrum؛ EURC إن خدمنا EEA).
5. ✅/❌ حساب EMI/بنكي مع إفصاح مسبق عن تدفقات المشفر.

إلى أن تكتمل هذه البنود: **لا ننشر أسعاراً، لا ننشئ فواتير حقيقية، لا نستقبل أموالاً.**

## 10. نتيجة بوابة القرار — 2026-11-18 (الوجهة: ليبيا → محفظة self-custody)

البحث هذه المرة استهدف مساراً واحداً: **بطاقة Visa/Mastercard → USDC → محفظة المالك**، مع قبول مالك/كيان في ليبيا. النتيجة: **لا يوجد مزوّد رئيسي مُتحقَّق منه يغطي ليبيا اليوم**.

| المزوّد | الحكم | الدليل |
|---|---|---|
| **Mercuryo** (شريك NOWPayments الفعلي للفيات) | ❌ ليبيا في قائمة المحظورين صراحةً | صفحة "Where does Mercuryo operate؟"، مراجعة 04.11.2026 |
| **NOWPayments** | ⚠️ بوابة Krypto فقط تعمل، لكن مسار البطاقة يعتمد على Mercuryo المحظور في ليبيا | صفحة "How to accept fiat؟" تسمّي Mercuryo صراحةً؛ رسوم 1% + 1% تحويل + gas |
| **Alchemy Pay** | ❌ ليبيا في قائمة الدول غير المدعومة | B2B supported countries، تحديث 05.01.2026 |
| **Wert.io** | ❌ Fiat Onramp = ✗ في ليبيا (NFT Checkout فقط ✓) | docs.wert.io/docs/service-availability، تحديث 05.11.2026 |
| **Dodo Payments** | ❌ ليبيا غير مدرجة في الدول المقبولة لحساب التاجر | accepted-countries-and-territories |
| **BitPay** | ❌ لا يقبل بطاقات/ACH/PayPal في فواتير التجار — مشفر فقط | support.bitpay.com، تحديث 13.11.2026 |
| **CoinGate / Coinbase Commerce** | ❌ لا مسار بطاقة مباشر للقبول (Commerce أُغلق 31.03.2026) | تحقق سابق + وثائق المزوّدين |
| **Malum** | ⚠️ المرشح التقني الوحيد: card→crypto، USDC/Polygon في Payout API، تسجيل "GLOBAL" | docs.malum.co + دليل المزوّدين (مُطالب به من المزوّد) |

### تحذيرات Malum (إن دخلنا فيه)

- **الرسوم أعلى بكثير من معيار الدليل:** 5% + $0.5 (افتراضي) أو 6% + $0.3 عبر Stripe أو 7% عبر Wert، **+ 1% وgas على السحب** → TCO عملي ~**7–10%** مقابل 2.2–3.0% المستهدفة.
- **توقيع الـ webhook**: `md5(txn|timestamp|webhook_key)` — MD5 وليس HMAC؛ يجب إصلاح هذا الجانب الأمني قبل استقبال أي أموال حقيقية.
- **أهلية ليبيا غير معلنة**؛ يلزم تأكيد كتابي من المزوّد + معرفة أي طريقة بطاقة فعلياً متاحة لحامل بطاقة ليبي.
- البطاقات المحلية الليبية (LYD) غير مقبولة عموماً؛ الجمهور القابل للوصول = حاملو بطاقات أجنبية/الليبيون في الخارج (حسب Orchestrapay وDPay/mypay المحليين، تسوية نقدية فقط).

### المسارات المتاحة الآن

1. **مرحلي (موصى به): USDC/Polygon فقط أولاً** — فاتورة على السلسلة إلى محفظتك، صفر chargeback، صفر مشكلة أهلية مزوّد. البطاقات تُضاف لاحقاً عبر المسار 2.
2. **هجين من خطوتين للبطاقات**: بوابة بطاقات مقبولة في ليبيا (Orchestrapay للبطاقات الأجنبية، أو DPay/mypay/Neom محلياً) → نقد في حساب بنكي/EMI → شراء USDC/Polygon وتحويله لمحفظتك. متوافق مع الدليل لكنه يحتاج EMI + إفصاح عن مصدر الأموال، وتسوية غير لحظية.
3. **Malum مباشر**: بطاقة → USDC/Polygon → محفظتك. الأسرع تقنياً، لكن يجب أولاً: تأكيد أهلية ليبيا كتابياً، وتوقيع webhook آمن، وموافقة على التكلفة الأعلى.
4. **تأجيل الدفع** والبدء ببوابة التسجيل/الحصص.

> لم يُعتمد أي مزوّد بطاقات بعد؛ لا تُنشر أسعار بطاقات ولا تُستقبل أموال عبر البطاقة قبل اختيار مسار وتأكيده.

## 11. التنفيذ الحالي — USDC/Polygon مباشر إلى محفظة self-custody (2026-11-18)

تم تطبيق المسار **1 (مرحلي / موصى به)** من §10. لا يوجد مزوّد دفع، ولا webhook، ولا مفتاح خاص في الـ Worker: الـ Worker **يقرأ فقط** بيانات السلسلة العامة ويرصد تحويلات USDC الواردة إلى عنوان المالك.

### الثوابت

| العنصر | القيمة |
|---|---|
| الشبكة | Polygon PoS (`chainId 137`) |
| العملة | USDC الأصلي من Circle |
| العقد | `0x3c499c542cEF5E3811e1192ce70d8cC03d5c3359` |
| عنوان الاستلام | `0xc6240d79d9341d6e585ca1ddb9b121c8c8a130d4` (عنوان EVM من صفحة donatr.ee؛ المالك أكّد دعم Polygon) |
| التأكيدات | 64 (`PAY_CONFIRMATIONS`) |
| نافذة Quote | 15 دقيقة |
| نافذة قبول الدفع | 24 ساعة |
| الحزم | `5$ → 100`، `10$ → 250`، `25$ → 700` اعتماد |

المصدر المشترك للواجهة والـ Worker: `src/config/plans.js`. في الإنتاج يمكن تجاوز العنوان عبر متغير `PAY_RECEIVE_ADDRESS` دون تغيير الكود.

### لماذا المبلغ الدقيق إلزامي

كل فاتورة تحصل على **لاحقة عشوائية من 4 أرقام بالوحدة الصغرى لـ USDC** تُضاف إلى سعر الخطة؛ مثال: `5.002695 USDC`. هذه اللاحقة هي هوية الفاتورة، لذلك يجب أن يكون المبلغ **مطابقاً تماماً** (`underpaymentTolerance = 0`). أي نسبة تسامح — حتى 0.1% — ستتداخل مع الفواتير المجاورة وتنسب الدفع لحساب خاطئ. رسوم Gas تُدفع منفصلة بـ POL، لذلك لا حاجة لتقليل مبلغ USDC.

> تنسيق `underpaymentTolerance: 0.015` الوارد في §2 يخص فواتير الأسعار المقتبسة في مسار البطاقة/المزوّد، **وليس** هذا المسار المباشر.

### آلية التسوية

1. `POST /pay/invoice` ينشئ فاتورة بحالة `pending`，`pay_amount` فريد، و`created_block` من أحدث كتلة عبر RPC.
2. كل 3 دقائق (`crons: ["*/3 * * * *"]`) يستدعي الـ Worker `scanPending()`؛ و`GET /pay/status` يمكنه أيضاً فحص فاتورة `pending` مرة كل 10 ثوانٍ.
3. الفحص يستخدم `eth_getLogs` على عقد USDC مع topics: `Transfer`، `from = any`، `to = عنوان المالك`، ثم يقارن `data` كـ BigInt بالمبلغ المطلوب.
4. عند المطابقة تُحدَّث الفاتورة إلى `detected` ويُسجَّل hash المعاملة والكتلة والدافع في `invoice_events`.
5. عندما يصبح الفرق بين كتلة الرأس وكتلة الاكتشاف ≥ 64، تُمنح الاعتمادات **مرة واحدة** عبر **D1 batch ذري**: `credit_grants` + `credit_grant_applications` (ب-token فريد) + تحديث `paid_credits` + تحديث الفاتورة إلى `paid` + حدث `credited`. أي فشل في أي عبارة يُرجع الدفعة كاملة، وأي إعادة فحص لا تمنح رصيداً مرتين.
6. `/ai` يستهلك **الاعتمادات المدفوعة أولاً** بتحديث شرطي ذري (`remaining >= cost`)، ثم يرجع إلى الحصة المجانية اليومية عند نفادها. استجابة `/ai` تتضمن `quota.paid_remaining` و`quota.source = "paid" | "account" | "visitor"`.

### المتغيرات والـ secrets

```jsonc
// worker/wrangler.jsonc (vars)
"PAY_RECEIVE_ADDRESS": "0xc6240d79d9341d6e585ca1ddb9b121c8c8a130d4",
"POLYGON_RPC_URL": "https://polygon-bor-rpc.publicnode.com,https://polygon-rpc.com",
"PAY_CONFIRMATIONS": "64",
"PAY_SCAN_BLOCKS": "2000"
```

- `POLYGON_RPC_URL` قائمة مفصولة بفواصل مع fallback. الافتراضي: `polygon-bor-rpc.publicnode.com`، `polygon-rpc.com`، `rpc.ankr.com/polygon`. ملاحظة محلية: `polygon-rpc.com` أعاد `401` وBlockscout API أعاد `403`، لذا يُفضَّل publicnode.
- `PAY_SCAN_BLOCKS` يحدّد أقصى نطاق كتل لكل فاتورة في الدفعة الواحدة (الحد الأعلى 5000).
- اختياري: `npx wrangler secret put PAY_ADMIN_TOKEN` لتفعيل `POST /pay/scan` يدوياً؛ بدونه يكون المسار مخفياً (404). **لا تضع التوكن في `vars`.**

### الجداول الجديدة

`worker/schema.sql` يضيف: `invoices`، `invoice_events`، `credit_grants`، `credit_grant_applications`، `paid_credits`. يجب تطبيق الملف على D1 المحلي والبعيد قبل Deploy (الأمر في [README.md](../README.md)).

### الواجهة

زر **الاعتمادات** (`Zap`) في الهيدر يفتح `PlansDialog`: اختيار الخطة، نسخ المبلغ والعنوان، عدّاد الوقت، تحذير صريح بnetwork Polygon وUSDC الأصلي، رابط المعاملة، وزر «تحقق الآن» مع polling تلقائي كل 8 ثوانٍ. النصوص EN/AR كاملة في `src/i18n/dictionaries.js` تحت `pay.*`.

### نتيجة الاختبار المحلي

- فاتورة تجريبية بحالة `detected` انتقلت إلى `paid` ومنحت **100 اعتماد** بعد تفعيل الدفعة الذرية.
- إعادة التشغيل (rescan) لم تمنح رصيداً إضافياً (`credited: 0`) — idempotent.
- `/ai` باستخدام نموذج تكلفته credit واحد أنقص الرصيد `100 → 99` وترك عدّاد الحصة المجانية دون تغيير.
- بعد ضبط الرصيد المدفوع إلى 0، عاد `/ai` إلى الحصة المجانية وزادها `2 → 3`.
- `npm run lint` و`npm run build` نظيفان بعد التغييرات.

### ما لم يتحقق بعد

- لم تُستقبل أموال حقيقية؛ الاختبار كان بمحاكاة حدث على قاعدة محلية.
- المعالجة القانونية/الضريبية لتلقي USDC في ليبيا ما زالت مفتوحة (§10). لا يوجد KYC/AML في هذا المسار لأنه تحويل مباشر من محفظة المستخدم إلى محفظة المالك، وليس عبر CASP.
- بطاقات Visa/Mastercard ما زالت محجوبة في ليبيا (§10)؛ لم يُنشر أي سعر بطاقة.
- تحويل الاعتمادات إلى اشتراكات، واسترداد مدفوعات USDC، وسياسة «الدفع المتأخر» تحتاج قرار تجاري منفصل.
